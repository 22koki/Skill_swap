# SkillSwap — closed beta deployment guide

This repository contains **deployment configuration only**. No production hosting, database, domain, secrets, or monitoring service has been provisioned.

## Prerequisites

- The integration PR into `main` has been reviewed, passed GitHub checks, and merged.
- A managed PostgreSQL instance and managed Redis instance are provisioned, backed up and accessible to the application.
- A backend host capable of running an ASGI app, HTTPS and WebSocket upgrades (Render is described below).
- A frontend host for Vite static assets (Netlify is described below).
- Secret management, least-privilege credentials, cost limits, uptime monitoring and an alert destination.

## Backend: Render

1. Use the repository's `render.yaml` as a starting Blueprint for the Python web service. The service root is `backend`.
2. Create PostgreSQL and Redis first, then set their respective `DATABASE_URL` and `REDIS_URL` values from the hosting dashboard. Redis must be reachable from the backend and is used for both Channels and rate-limiting cache.
3. Set `DJANGO_ALLOWED_HOSTS` to your exact backend hostname only, e.g. `skillswap-api.onrender.com` (no URL scheme).
4. Set `DJANGO_CORS_ALLOWED_ORIGINS` to the exact HTTPS frontend origin, e.g. `https://skillswap-preview.netlify.app`.
5. `DJANGO_SECRET_KEY` is generated by the Blueprint. Do not store it in the repo or frontend configuration.
6. Confirm `DJANGO_TRUST_PROXY=True` is safe for the chosen hosting proxy; it must sanitize incoming `X-Forwarded-Proto`. Otherwise set it to `False` and configure HTTPS termination appropriately.
7. The build installs requirements and collects WhiteNoise static files. For the **single-instance beta**, the start command runs `python manage.py migrate --noinput` before launching Daphne, which serves HTTP and WebSockets through `config.asgi:application`. If migrations fail, the server does not start.
8. Visit `https://YOUR_BACKEND/api/health/` and confirm status `ok`. Run `python manage.py check --deploy` in a release environment using the production variables before inviting users.

**Provisioning note:** the Blueprint references existing managed PostgreSQL and Redis through environment variables. It does not automatically provision either database or Redis. Render's `preDeployCommand` is a paid-service feature; this starter avoids it by migrating at startup. **Use one application instance only**, and use a paid pre-deploy migration step or dedicated migration job before scaling beyond a single beta instance. Database migrations should be backed up and rehearsed before releases. Some hosting choices have costs; check pricing before creating resources.

## Frontend: Netlify

1. Connect the same GitHub repository and use the root `netlify.toml` (base `frontend`, build `npm run build`, output `frontend/dist`).
2. Configure `VITE_API_BASE_URL=https://YOUR_BACKEND/api` as a **build-time** Netlify environment variable, then trigger a fresh deploy.
3. Confirm the HTTPS frontend calls your backend URL, and WebSocket connections use `wss://YOUR_BACKEND/ws/...`.
4. Test browser refresh, mobile layout, login, notifications, private chat and Skill Circle chat.

## Closed-beta acceptance

- Create two test users and check complete signup, login, skill matching, swap acceptance, scheduled session, messages, review and Skill Passport.
- Test that another user cannot access private messages, bookings, saved collections or private Circles.
- Test refresh-token rotation, logout and re-login across separate browsers.
- Verify CORS, HTTPS, WSS, origin validation, migrations, Redis, notifications and persistence across restarts.
- Check that the production logs redact `Authorization` and `Sec-WebSocket-Protocol` headers.
- Set uptime/error alerts and verify PostgreSQL backups and a sample restore.
- Avoid inviting real users until the documented security limitations are accepted and mitigated.

## Blocking risks / follow-up

- The app currently stores JWTs in browser `localStorage`. Consider HttpOnly cookie-based session architecture and CSRF protection before public launch.
- WebSocket authentication transmits the access token in the protocol header. The header must be excluded from all proxy and APM logs.
- Logout revocation is best-effort if an access token is already expired or connectivity is lost.
- In-memory local Redis fallback is development-only. Production requires managed Redis.
- Configure admin access, an incident contact, retention policies and run a complete dependency/security audit.

See `SESSION_SECURITY.md`, `SECURITY_AUDIT.md` and `RELEASE_READINESS.md`. Passing tests does not constitute security certification.
